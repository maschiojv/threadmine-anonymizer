# Threat model

This document exists so a security reviewer can approve or reject `tm-anon` on
facts. It is written to be pessimistic: the useful part is the list of things
this tool does **not** protect you from.

Short version: **this is pseudonymization that you, and only you, can reverse.**
It is not irreversible anonymization, and anyone claiming otherwise about a tool
that also offers an `unmask` command is selling something.

---

## 1. What the tool does, in security terms

| | |
|---|---|
| Secret | A 256-bit key generated by `SecureRandom` at `tm-anon init`, stored in the vault file. |
| Transform | `token = firstBits(HMAC-SHA256(key, type ‖ ":" ‖ canonicalValue))`, rendered as `[pCmt]` + 10 hex characters with an `x` in the middle (`C8ce34x79651`). 14 hex on the collision path. |
| Reversal | Dictionary lookup in the vault's `map`. HMAC itself is one-way; the vault is what makes `unmask` possible. |
| Trust boundary | Your filesystem. The tool has no network capability at all, and a build-failing test enforces that (`NoNetworkArchitectureTest`). |
| Legal framing | Pseudonymization under GDPR/LGPD from the data controller's side; effectively anonymous data for any party without the vault, including the analysis service. |

The source code contains **no secret** (Kerckhoffs's principle). Publishing the
algorithm, the allowlist and the whole implementation costs nothing, because
security rests entirely on the key.

## 2. Who can undo the masking

**1. A third party with the tool and the masked dump: cannot.**
Reversal requires the vault. Without the key they cannot even *test a guess*.
This is the reason the scheme uses keyed HMAC and not a plain hash: Java
identifiers are highly guessable (limited vocabulary, camelCase, package names
derived from the company domain), so `SHA-256("com.acme.OrderService")` would be
a solved dictionary attack. `HMAC(key, …)` is unverifiable without the key at any
computational budget. Truncating to 40 bits does not change that — it changes
collision probability, not invertibility.

**2. Whoever holds the vault: undoes everything.**
The reverse map is literally inside it. "It only exists on the machine that
masked the dump" is not a property of the machine, it is possession of a file.
Sharing the vault with your team (a supported and recommended workflow) is a
deliberate decision to share reversal capability. A leaked vault means total
reversal of every dump ever masked with it. **Treat the vault as a private key:
back it up, keep it out of repositories and tickets, put it in the same place you
keep other secrets.** Passphrase encryption of the vault at rest is planned, not
implemented — until it lands, the file's confidentiality is entirely up to your
filesystem and your secret store.

**3. The analysis service itself: cannot**, even if fully compromised. It only
ever receives tokens, and no amount of server-side access produces a key that
was never sent.

## 3. What a leaked masked dump still reveals

Masking hides names. It does not hide structure, and structure is information:

- **Which frameworks you run.** The allowlist is verbatim by design, so
  `org.apache.tomcat…`, `io.netty…`, `org.hibernate…`, `kafka…` frames stay
  readable. This is how detection keeps working. `--strict` tokenizes the
  *recommended* tier (52 common open-source prefixes) if you would rather not
  disclose your library stack; the *required* tier can never be tokenized without
  breaking analysis.
- **Shape of the application.** Thread counts and states, pool names and sizes
  (`t426f3xd05a4-1..N` is obviously a pool of N), depth of your package tree
  (each segment is a separate token), how many distinct classes appear in a
  stack, presence of a deadlock.
- **Environment metadata.** JVM version and vendor from the dump banner,
  timestamps, `cpu=` / `elapsed=` timings, thread priorities, daemon flags, port
  numbers embedded in server pool names (`http-nio-8080-exec-1`).
- **Linkability.** Two dumps masked with the same vault produce the same tokens.
  That is a deliberate feature (it is what makes diffs and timelines work), and
  it is also a correlation channel: an observer holding several masked dumps can
  tell they came from the same application and track the same class across them.
  Masking with a different vault per application limits this; there is no way to
  have both linkability and unlinkability.

This is exactly the view the analysis service gets. It is a much smaller surface
than the raw dump, and it is not zero.

## 4. Residual risk: re-identification by correlation

An adversary who *also* possesses a raw dump of the same application, obtained by
some other route, can attempt to re-label tokens by structural correlation:
frequency of frames, position relative to framework frames, stack shapes,
pool sizes. Given a raw dump, `token → real name` becomes largely a matching
problem, not a cryptographic one.

This is the generic weakness of any pseudonymization scheme. It requires
auxiliary material the attacker normally does not have — and if they already have
your raw dump, the masked one is not what is hurting you. Stated here because a
threat model that omits it is not a threat model.

Also worth stating: names are hidden, and a *sufficiently distinctive structure*
is not. If your application is the only Java program in the world with a
particular exotic stack, that stack identifies it, tokens or not.

## 5. What leaves your machine

`tm-anon` never sends anything. This section is about what **you** send when you
upload the masked file it produced.

### Leaves, in the masked file

| Category | Why it stays |
|---|---|
| `Full thread dump …` banner, JVM version and vendor | format anchor; the analyzer needs it to parse at all |
| `java.lang.Thread.State:`, state qualifiers, blank-line structure | thread delimitation and state detection |
| JDK, framework and library frames (required allowlist) | every name-based detection keys off these |
| Lock addresses `<0x…>`, `- locked` / `- parking to wait for` markers | contention and deadlock analysis group by address |
| Thread name **suffixes** (`-1`, `#7`) and pool shapes | pool grouping, starvation, thread-leak detection |
| `prio=`, `daemon`, `cpu=`, `elapsed=`, `tid=`, `nid=`, timestamps | timing and metadata; used by the UI and some heuristics |
| Loom markers: `<pinned: synchronized>`, carrier-thread lines | virtual-thread analysis |
| Tokens `[pCmt]…` in place of your names | opaque without the vault |

### Removed entirely (stripped, zero analytical cost)

These carry your data and no analyzer reads them, so they are deleted and
replaced by `# [tm-anon: stripped]`:

- `Threads class SMR info` / `_java_thread_list` blocks (raw addresses)
- `JNI global refs`
- `Locked ownable synchronizers` sections (leak lock class names)
- `Compiling: … com.app.Class::method` compiler lines (leak your class names in
  a place nobody looks)
- Heap / Isolates sections

### Redacted (fail-closed)

Any line no rule classifies is replaced by `# [tm-anon: redacted]` and counted in
the report. The tool never passes an unrecognized line through verbatim, and it
never guesses at an unrecognized file format — it exits with code `2`.

### Does **not** leave, ever

Your vault. There is no code path that reads it and writes it anywhere but the
path you passed on the command line.

### Leaves outside the file, and `tm-anon` cannot help you

- **The upload file name.** `payments-prod-tenant-acme.txt` undoes the whole
  exercise. `mask` prints a reminder on every run for this reason.
- **The analysis title and description you type into the UI.** They flow into
  comparison headers, AI prompts, exports and shared snapshots.
- **Whatever you paste into a support ticket.** Same rule: mask first.

## 6. Assumptions and non-goals

Assumed:

- Your machine is not already compromised. A tool running on a compromised host
  protects nothing, and this one is no exception.
- Your JDK's `SecureRandom` is sound.
- You keep the vault as a secret and back it up.

Explicit non-goals:

- **Not irreversible anonymization.** Reversibility is the point.
- **No confidentiality of the vault at rest** (yet). No passphrase encryption in
  this version.
- **No protection against structural inference** (sections 3 and 4).
- **No masking of dialects it does not support.** GraalVM native-image dumps are
  refused, not partially masked. Anything the format detector does not recognize
  is refused with exit `2` rather than half-masked.
- **OpenJ9 javacore is supported in strip mode, and the trade is worth stating.**
  A javacore carries command lines, `-D` properties, full classpaths, monitor
  tables with your class names, and loaded-class listings — far more than a
  HotSpot dump. `tm-anon` keeps only the title (minus the local file path, which
  is redacted) and the thread section; every other section is removed wholesale
  and replaced by a single `# [tm-anon: stripped section <NAME>]` marker, and an
  unrecognized section is stripped rather than kept. Two consequences to know
  about: the JVM version line lives in a stripped section, so an analyzer may
  report an unknown Java version; and the explicit `1LKDEADLOCK` block is
  removed with the lock section — the deadlock cycle survives in the crossed
  `3XMTHREADBLOCK` lines, which is what the analyzer reads anyway.
- **No PDF or rendered-report unmasking.** `unmask` operates on text.

## 7. How to audit this in an afternoon

1. `./mvnw test -Dtest=NoNetworkArchitectureTest` — proves no network code in
   sources, bytecode or dependencies. Read the test; it is short.
2. `grep -rn "java.net" src/main/java` — expect nothing.
3. Read `pom.xml` — one dependency, JUnit, test scope.
4. Read `allowlist/allowlist-v1.json` — everything that stays verbatim, with
   provenance in `allowlist/SOURCES.md`.
5. Read `src/main/java/dev/threadmine/anon/core/HmacTokenEngine.java` and
   `Vault.java` — the entire cryptographic surface, a few hundred lines.
6. Run `tm-anon mask` on one of your own dumps, then `tm-anon verify original
   masked`, and read the masked file yourself. Residual identifiers must be `0`.

Step 6 is the one that matters. Do not take this document's word for it: the
tool ships the verification command precisely so you do not have to.

## 8. Reporting a problem

If `tm-anon` leaks an identifier it should have masked, that is a security bug.
Open an issue with a **synthetic** reproduction (fictional `com.acme.*`
namespace, in the style of `corpus/fixtures/`). Never attach a real dump to a
public issue — it would be an ironic way to prove the point.
